# RewindSafe backend comparison

This review compares the extracted RewindSafe tree at `/private/tmp/flow-comparison/rewindsafe-master` with the VeerIQ source in this repository. It is a source and artifact review, not a fresh runtime verification. I did not inspect environment files, start services, install dependencies, or make live calls. References use repository-relative paths and one-based line numbers.

## Assessment

RewindSafe is the stronger backend for a consequential, state-changing workflow. Its sole executor commits a snapshot-derived repair inside a PostgreSQL transaction with row locking, idempotency, revalidation, column privileges, and tenant row-level security (`backend/rewindsafe/workflows/rewindsafe/executor.py:1-21`; `backend/migrations/002_executor_hardening.sql:8-25`). The dispatcher reruns admission after approval and refuses if the current payload or state differs (`backend/rewindsafe/runtime/dispatch.py:979-1012`). That database-enforced last boundary is RewindSafe’s strongest actual differentiator over VeerIQ’s local synthetic research sandbox.

VeerIQ has the clearer, more focused demonstration of a model-proposed research workflow: a provider-backed tool loop exists in `server/engine.mjs:60-71`, but its included benchmark explicitly measures a local protocol gate rather than a live model or ArmorIQ (`docs/benchmark-results.json:2-5`). RewindSafe has a real LLM implementation too (`backend/rewindsafe/agent/planners.py:610-759`), and its saved live injection evaluation records Groq-hosted `openai/gpt-oss-120b` proposing the injected `restore_access_grant` tool in all three task-only trials; live ArmorIQ plan binding blocked each proposal (`evidence/injection-eval-20261007T162005Z.json:1-102`). The same artifact records no such proposal from Qwen in three task-only trials. This is direct evidence of a live model proposing an injected forbidden action in this small evaluation. It is a first-decision-turn experiment: tools were not executed and it does not demonstrate end-to-end model recovery. The separate live flagship run remains a scripted re-enactment (`evidence/live-flagship-2026-10-07.json`, `run.planner` and `run.metadata.planner_label`; `backend/tests/live/test_live_flagship_run.py:1-5`). VeerIQ has no checked-in live model evaluation.

## ArmorIQ and the trust boundary

RewindSafe’s ArmorIQ integration is a genuine SDK integration in the checked-in evidence: the saved run records `mode: live`, `session_mode: sdk`, `sdk_version: 0.6.10`, a backend plan hash and token ID, six non-simulated enforcement checks, and one plan-binding denial (`evidence/live-flagship-2026-10-07.json`, `plan` and `metrics`). The gateway source implements plan issuance, per-tool checks, status classification, delegation polling, reporting, and fail-closed behavior (`backend/rewindsafe/runtime/armoriq_gateway.py:105-198, 607-731, 735-778`). Its honest boundary is tool-name binding: parameters are separately enforced by RewindSafe’s grant and domain layers (`armoriq_gateway.py:14-16, 648-651`; `backend/rewindsafe/workflows/rewindsafe/adapter.py:79-145`).

The recorded live flagship run demonstrates plan issuance, in-plan ALLOW, SDK plan-binding BLOCK, and successful repair, but it used the scripted planner; the source test says so directly (`backend/tests/live/test_live_flagship_run.py:1-5`). A separate saved live Groq evaluation does demonstrate one model proposing the injected forbidden call in 3/3 task-only first-turn trials and live ArmorIQ blocking each proposal (`evidence/injection-eval-20261007T162005Z.json:1-102, 394-398`). Qwen proposed no forbidden call in 3/3 task-only trials (`:104-151`). The experiment explicitly says tools were not executed and only the first decision turn was tested (`:394-398`), so it does not establish full-run recovery behavior. Neither artifact demonstrates an ArmorIQ HOLD or its approval round trip. Live Gate A source probes require a configured key and make actual live checks (`backend/tests/live/test_gate_a_live.py:1-5, 58-103`); they were not run as part of this review.

VeerIQ imports `@armoriq/sdk`, starts an SDK session, captures a plan, and calls `session.check` in live mode (`server/armoriq.mjs:1-13`). Its enforcement composition is compact and sensible: protocol DENY dominates, sponsor DENY/unavailable fails closed, and only ALLOW reaches the MCP sandbox (`server/dispatcher.mjs:5-25`). Its saved evidence does not establish that this live path was exercised. The benchmark states it is a local protocol gate and excludes live ArmorIQ/model evaluation (`docs/benchmark-results.json:2-5`).

## Approval and effects

RewindSafe approvals have an explicit second-person boundary: reviewer role, same tenant, and requester/approver separation (`backend/rewindsafe/runtime/approvals.py:46-59`); the API route also requires reviewer identity and checks tenant (`backend/rewindsafe/api/routes_approvals.py:39-49`). Payload digest and state constraints are compared, and the dispatcher repeats ArmorIQ, grant, and domain checks after approval (`approvals.py:62-70`; `backend/rewindsafe/runtime/dispatch.py:979-1009`). The executor opens and owns the transaction, checks preconditions, then sets `rs_executor` and applies tenant-scoped updates (`backend/rewindsafe/workflows/rewindsafe/executor.py:218-263, 434-459`).

VeerIQ creates a pending approval bound to a call hash and artifact hash, uses a lock against simultaneous clicks, expires it, and performs a fresh dispatch check before publishing (`server/engine.mjs:33-39, 73-89`). In its checked-in API, however, anyone able to reach `POST /api/runs/:id/approval` can submit the boolean and matching pending values; there is no reviewer login, identity, or role check (`server/index.mjs:25`). Both local apps bind to loopback, which reduces exposure in the demo, but does not create a reviewer identity boundary.

VeerIQ’s MCP process separation is a useful containment boundary: effect handlers are not imported by the API and model-controlled destinations do not determine the canary URL (`server/tools.mjs:7-14, 29-33`; `server/transport.mjs`). Its handlers still keep runs/effects in memory (`server/tools.mjs:8-9`), and the API’s SQLite run store persists run snapshots/events but not MCP state (`server/store.mjs:6-18`). A restart interrupts held work and leaves prior process-local effect counters unavailable, as VeerIQ’s architecture document acknowledges (`docs/architecture.md:79-84`). RewindSafe persists its domain state, approvals, manifests, and receipts in PostgreSQL and exercises concurrent, stale, duplicate, wrong-tenant, and privilege cases in acceptance tests (`backend/tests/acceptance/test_runs_end_to_end.py:26-43`; `backend/tests/acceptance/test_concurrent_apply.py`; `backend/tests/acceptance/test_postgres_column_privilege.py`).

## Evidence and remaining gaps

RewindSafe’s acceptance suite is broad on paper and directly asserts no prohibited handler entry, no protected-state violations, and zero forbidden effects (`backend/tests/acceptance/test_runs_end_to_end.py:26-43`). The boundary run test additionally requires all 12 probes to pass (`:45-56`). I did not execute these tests: the suite requires PostgreSQL fixtures, which this review was instructed not to start. The saved live artifacts are concrete evidence for the recorded ArmorIQ checks and single-turn model proposals, but should still be treated as checked-in run artifacts rather than results reproduced in this review. The injection evaluation covers two models with three task-only first-turn trials apiece, plus three trials per model with policy briefing; it is a small behavioral sample, not a general prompt-injection success rate.

VeerIQ’s 37/37 benchmark is a checked-in result, not freshly reproduced here, and its own metadata narrows the claim to constructed local protocol cases (`docs/benchmark-results.json:2-20`). The E2E source test is stronger than a mocked handler test: it creates the real MCP sandbox and asserts denied effects, single exact publication, receipt integrity, rejection/expiry, positive control, and restart invalidation (`tests/boundary.test.mjs:58-75`). It was not run for this review.

RewindSafe’s key follow-up is to record one live LLM run and configure a real ArmorIQ HOLD policy, then verify the complete sponsor approval round trip. It also needs real authentication and a second workflow before claiming general deployment readiness; its own limitations call out local demo identities, one workflow, and synthetic data (`docs/limitations.md:7-10, 21-29`). VeerIQ’s next steps are to add reviewer identity/authorization and durable effect storage, then produce reproducible live model and ArmorIQ evidence. Its clearest advantage today is a small local research demo with a model loop and isolated MCP effect process; its strongest security proof in the repository remains the deterministic local protocol boundary, not sponsor enforcement.
