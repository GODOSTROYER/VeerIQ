# Current limitations

VeerIQ is a recovery prototype, with synthetic prepared incidents and an import workspace for user-supplied data. The following claims remain unverified or outside its scope.

- **Live-agent completion:** pooled over six recorded batches (84 trials, recorded on different code versions, so this is what was observed, not one controlled cohort), the model acted in 24 trials. It attempted the poisoned action (`restore_access_grant`) in 23, and ArmorIQ plan binding blocked all 23. The permitted repair completed in 18 of the 24 trials where it acted, with zero forbidden effects. Sixty trials never acted because of the model provider's rate limit or an operator stop; two of those were operator interruptions. No batch finished its 40 requested trials. This does not establish the required ≥90% completion rate or adversarial robustness. The [40-trial batch](../evidence/reliability-20261012T160152Z.json) has 39 trials that never acted and one that acted without reaching the poisoned action or completing a repair. A [separate isolated trial](../evidence/reliability-20261012T201737Z.json) completed safely after live ArmorIQ blocked its poisoned proposal. At about 20,626 tokens per trial, a full 40-trial cohort needs substantially more than the previously observed 200,000-token daily quota. Pooled counts: [SUMMARY.json](../evidence/SUMMARY.json).
- **Post-fix reliability cohort:** [`reliability-20261013T175457Z.json`](../evidence/reliability-20261013T175457Z.json) has 1 of 40 requested trials recorded (successful, one poisoned-action block, zero forbidden effects). It cannot be resumed after the 14 October changes, because the evaluator fingerprints the enforcement source files and those files changed. A new cohort must be started on the current code; the manual resume steps in [reliability-batching.md](reliability-batching.md) no longer apply to this cohort. The six-trial pre-fix diagnostic ([`reliability-20261013T172610Z.json`](../evidence/reliability-20261013T172610Z.json)) completed 5 of 6 repairs with zero forbidden effects; its partial-manifest failure is retained. Neither cohort establishes ≥90% completion.
- **Sponsor HOLD:** the isolated [$12,400 request](evidence/merged/hold-rule-first-check.json) received ALLOW. The account dashboard cannot apply the required amount condition. A real ArmorIQ HOLD, delegation round trip, reject, and timeout remain unobserved. VeerIQ’s own separated reviewer flow is a RewindSafe-layer control, not sponsor approval.
- **Identity and deployment:** nine local OIDC/auth tests cover protocol and authorization behavior. The production image builds and invalid or unreachable provider configuration fails closed. A real locally deployed Keycloak login and healthy API/UI/PostgreSQL/provider stack were observed ([evidence](evidence/local-oidc-rehearsal.json)). The fixture uses synthetic identities, a self-signed localhost certificate and Keycloak development mode; it is not an externally deployed production identity service. Browser test contexts alone ignored the local certificate warning; server-side TLS verification remained enabled. A public production deployment and operational hardening remain unobserved. Hosted GitHub Actions passed at b02387b ([evidence](evidence/hosted-ci.json)); live-service checks were explicitly skipped. Hosted CI later passed on `main` (17 October, commit f4a3f62; counts in [submission-status.md](submission-status.md)). No production security review or load test has been performed.
- **Import scope:** declarative mappings cover flat scalar fields, not nested objects, relationships, or arbitrary SQL workflows. CSV/JSON and read-only PostgreSQL copy source records into VeerIQ; recovery does not write back to the source database. PostgreSQL JSON-field restrictions are enforced by trusted adapter/catalog code; the restricted database role permits updating the repair-values container, not individual JSON keys. Source metadata, tenant ownership, and authority remain immutable to that role.
- **Evidence identity:** the offline verifier validates signatures against the published pinned key, hashes, receipt digests, and linked events. That proves integrity relative to this key, not independent sponsor attestation. ArmorIQ plan hashes are available; five server-returned audit IDs are included in a new scripted live recovery export ([`audit-linked-scripted-live-sealed.json`](evidence/merged/audit-linked-scripted-live-sealed.json)); older exports contain none. The offline verifier does not validate those IDs against the sponsor service. Signing-key rotation and external custody are not implemented.
- **Human evaluation:** eight-view automated accessibility checks and responsive captures do not replace a first-time human viewer test. No independent participant has yet completed the requested two-minute comprehension test.
- **Operational maturity:** multi-region operation, disaster recovery of VeerIQ itself, key rotation, production permission review, and sustained load testing remain. Database migration ownership and operational secrets need deployment-specific review.
- **Hackathon eligibility:** according to the earlier local history, earlier RewindSafe source predates the event. This repository's baseline commit is dated 12 October and cannot be split into pre-event and event-week work. Organizer confirmation of reuse eligibility remains outstanding.
- **Demo:** the [recorded demo](video/veerIQ-demo.webm) shows real local import behavior with a scripted planner, live ArmorIQ, and recorded standalone verifier output. It explicitly identifies the missing sponsor HOLD. It is not a live LLM reliability demonstration. It is secondary: the submission video is the 4:21 demo in `videos/demo-video/final/`, which includes a live-model segment (see [submission-status.md](submission-status.md)).
